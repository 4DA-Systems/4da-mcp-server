# @4da/mcp-server

[![npm version](https://img.shields.io/npm/v/@4da/mcp-server?color=gold)](https://www.npmjs.com/package/@4da/mcp-server)
[![License: Apache-2.0](https://img.shields.io/badge/License-Apache--2.0-blue.svg)](LICENSE)
[![Node](https://img.shields.io/badge/Node-%3E%3D22-brightgreen)](https://nodejs.org/)
[![CI](https://github.com/4DA-Systems/4da-mcp-server/actions/workflows/ci.yml/badge.svg)](https://github.com/4DA-Systems/4da-mcp-server/actions/workflows/ci.yml)

**Upgrade intelligence for AI coding agents.** Before your agent bumps a dependency it learns what changes between the version you run and the one you want, which of your files that touches, and which vulnerabilities the move fixes, from your own lockfiles, on your machine. Plus vulnerability scanning at osv-scanner parity on the lockfiles it reads ([what that covers, and how it is measured](#how-it-works)), ranked upgrade plans and decision memory. Zero config, no account.

```
You:     "Upgrade axum to 0.8"
Agent →  upgrade_impact { package: "axum", to_version: "0.8.4" }

         axum 0.7.9 -> 0.8.4: 5 releases (0.8.2 yanked), changelog from the 0.8.4 crate.
         12 breaking entries, 8 touch your code (Path, Query, Router, extract, serve):
           breaking  Remove OptionalFromRequestParts impl for `Query`        (you use Query)
           breaking  Require `Sync` for all handlers added to `Router`       (you use Router)
           ...
         Your code: 10 files import axum.
```

*(Output of version 6.0.0, abridged, from 2026-10-02 on the 4DA desktop app's repository, where this server lived until 2026-10-04. Later releases word the same answer a little differently (6.3.0 counts 11 breaking entries for this upgrade), and the files and symbols an answer names are your project's.)*

One command to install. No API keys. No accounts. Your code never leaves your machine.

## Install

Requires Node.js 22 or later; below it the server stops at once and says why (`--version` and `--help` still answer). CI runs the suite on Node 22 (the newest 22.x on Linux, Windows and macOS, and 22.12, where the server falls back to `better-sqlite3`) and on Node 24 (Linux); other versions are not tested.

The server uses Node's built-in `node:sqlite` (Node 22.13 and later), so it needs no install script and works with npm 12's default of blocking them. On Node 22.0-22.12 it uses the optional `better-sqlite3`, whose native module npm 10 and 11 build on install. `npx @4da/mcp-server@6.5.1 --doctor` shows which one is in use.

```bash
claude mcp add --scope user 4da -- npx -y --prefer-offline @4da/mcp-server@6.5.1
```

Every command and config on this page pins the version, and so do the plugin, the Gemini extension and the entry `--setup` writes, so what runs changes only when you change it. Each configuration starts the server with `npx -y --prefer-offline`: with `--prefer-offline` a cached copy of the pinned version starts without asking the registry first, which matters behind a slow or dead proxy. npx's own options go before the package name; written after it they are passed to the server, which exits with `unknown argument`. Without a version, npx runs whatever it has cached or the newest release, which you did not review.

To update, replace the version with the newest one on npm (`npm view @4da/mcp-server version`, or run `--setup --update` from the newer version, which rewrites the `4da` entry of the editor configs it finds and, for Claude Code, prints the commands that move the pin: `claude mcp remove` and `claude mcp add`, or the plugin's update); the [changelog](CHANGELOG.md) says what changed. A pinned install never updates itself, so the server says when a newer release is published: `get_context` carries `update_notice` (both versions and the command that moves the pin) and `--doctor` prints it as a "Server version" warning. The server reads the newest version from the npm registry only after a tool call of the session has already contacted a package registry, never at start-up and never with `FOURDA_OFFLINE`, at most once a day per data folder.

**As a Claude Code plugin** (the MCP server plus a hook):

```bash
claude plugin marketplace add 4DA-Systems/4da-mcp-server
claude plugin install 4da@4da
```

The hook runs before an edit or a command and stops a dependency version from being written or installed before `dependency_check`, or a `what_should_i_know` call that declared the package `public: true`, has cleared it. What it holds, what it lets through and what it does not see: [The guard hook](#the-guard-hook).

## How It Works

The server reads every lockfile of the project it is started in, including independently-locked projects below the root (a repo with `src-tauri/Cargo.lock` beside a root `pnpm-lock.yaml` is scanned whole): `package-lock.json` / `npm-shrinkwrap.json`, `pnpm-lock.yaml` (v5–v9), `yarn.lock` (v1 and berry), `bun.lock`, `Cargo.lock` (Cargo workspaces included), `poetry.lock`, `uv.lock`, `pdm.lock`, `Pipfile.lock`, requirements pins (`*requirements*.txt`, `requirements/*.txt`, with `-r` and `-c`), `go.mod` / `go.sum` (Go's build list), `Gemfile.lock` (RubyGems; git and path gems are local code, not releases) and `composer.lock` (Packagist). Every Python source in a folder is read, not only the first. Every installed copy is scanned, not one version per name, with the lockfile's own dev flags. It re-reads them whenever a lockfile changes, and for npm it also checks what `node_modules` actually holds. A lockfile is what is installed, so it is read whether or not `.gitignore` lists it, and a dot-directory (`.github/actions/*`) is a directory like any other; so are `build/`, `dist/`, `out/`, `coverage/`, `.vscode/` and `.idea/`, which are read unless the repository ignores them. What is not scanned is said, lockfile by lockfile, under `coverage.not_scanned.lockfiles` with a `reason`: a directory `.gitignore` excludes is left out (it is as often a scratch clone as the project's own code: `gitignored_directory`); installed code, a tool's build output or cache, and editor or agent state (`node_modules`, `target`, `.venv`, `.next`, `.claude` ...) are never scanned, and when the repository does not ignore such a directory the lockfiles in it are listed (`excluded_directory`; it is searched within 2,000 directories, and the answer says when that bound stopped it); a lockfile sitting directly in an ignored `vendor/`, `target/` or `venv/` is listed too (`output_directory`); version-control data is never entered. A junction or symbolic link whose real path is inside the project is followed, each directory walked once; one that leads outside it is not, and the lockfiles behind it are listed (`symlink_outside_root`); a directory the walk cannot list is named (`unreadable`, its path ending in `/`). A lockfile or manifest holding git merge-conflict markers is not read at all, neither side of it: it is listed with reason `merge_conflict`, `coverage.complete` is false and every tool says `NOT CHECKED (merge conflict)` for it. The walk goes 4 levels down and up to 256 projects; whatever it leaves out is listed the same way (`depth`, `project_limit`). So is every manifest with no lockfile: its declared ranges are not installs and are not scanned, its exact pins are checked but the packages they pull in are resolved nowhere (`coverage.unresolved_manifests`, and `coverage.manifests_without_lockfile` for a manifest in a subdirectory that no lockfile above holds as a workspace member). `vulnerability_scan` always returns a `coverage` block: a scan that left nothing out says `complete: true` with `lockfiles_read` (and `lockfiles_not_scanned: 0`), one that left something out says `complete: false` and lists it; nothing is dropped silently. So are manifests of ecosystems it does not read (Maven `pom.xml`, Gradle, .NET `*.csproj` / `packages.lock.json`, Pub, Hex, SwiftPM, CocoaPods: `coverage.not_covered`), lockfiles that exist but cannot be read (invalid JSON, Bun's binary `bun.lockb`: `coverage.unreadable_lockfiles`), lockfiles that are truncated or damaged and were read only up to the damage, that lack an entry another of their packages needs, or are older than their manifest (a dependency the manifest declares has no entry: `package.json` for npm, pnpm, Yarn and Bun lockfiles, `Cargo.toml`, `pyproject.toml` for uv, Poetry and PDM, `Pipfile`, `Gemfile` or `gems.rb`, `composer.json`; a version changed only in the manifest, with the old one still in the lockfile, is not detected) (`coverage.partial_lockfiles`), a second lockfile in a directory that disagrees with the one that was read (`coverage.conflicting_lockfiles`), requirements with no pinned version such as `pydantic>=2.0.0` (`coverage.unpinned_requirements`: there is no installed version to check), dependencies installed from git or a URL, gems from a `GIT` section and Composer branch checkouts (`coverage.not_checkable`: they are not the registry package of that name, so they are never matched against it), files of a supported ecosystem in a form that is not read (`environment.yml`, `setup.py`, `pylock.toml`), and lockfiles under test-fixture directories (`tests/`, `test/`, `fixtures/`, `testdata/`, `__fixtures__/`, `conformance/` ...), which are not scanned as the project's own unless you pass `include_test_fixtures: true` (`coverage.not_scanned`). Every lockfile problem listed here (unreadable, partial, conflicting, a refused include, a merge conflict, a conflicted `go.sum` included) also makes `upgrade_planner` say `vulnerabilityDataAvailable: false`: the plan and the scan read the same list. Each of them but a conflicted `go.sum` also starts the scan's answer with NOT CHECKED and makes its totals null, with what it found under `found_in_checked_dependencies`. A lockfile read whole that could only not be compared with its manifest (`not_cross_checked_lockfiles`) is a note: it changes neither the totals nor the plan.

Started in a workspace member that has no lockfile of its own, whose manifest an ancestor's lockfile holds as a member (npm, pnpm, Yarn and Bun workspaces, a Cargo workspace, a uv, Poetry or PDM workspace, a `go.work`), the server reads that workspace root and says so (`project_root` is the root; `vulnerability_scan`'s `workspace_note` and `dependency_health`'s summary name the member it was started in). The search stays inside the enclosing git repository, or at most 6 levels up with none, never at or above your home directory; an ancestor lockfile that cannot be confirmed to hold the directory is named in the coverage note, not read. When no lockfile was read for the project at all, no tool scores or clears it: `dependency_health` gives `healthScore: null` with `withheldReason: "no_lockfile"` and a NOT CHECKED summary (never "0 vulnerable"), a dependency known only by its declared range shows `currentVersion: null` beside `declaredRange`, `upgrade_planner` sets `vulnerabilityDataAvailable: false`, `what_should_i_know` never says `safe_to_delegate` on that basis, and `vulnerability_scan` starts its answer with NOT CHECKED and gives null totals (what it found among a manifest's exact pins is a lower bound, under `found_in_checked_dependencies`). A folder that holds nothing the server reads, an empty one or the wrong one, is answered the same way, never as a complete scan with zero findings.

**An incomplete answer is never a clean one.** When OSV.dev cannot answer for some dependencies (outage, HTTP error, timeout, the query budget), `vulnerability_scan` starts with `summary: "NOT CHECKED: ... N of M dependencies have no vulnerability answer"`, counts them in `coverage.unchecked_dependencies`, and sets `total_vulnerable_packages` and `by_severity` to null (what the checked part found is under `found_in_checked_dependencies`); `dependency_health` withholds its score and vulnerable count, and `upgrade_planner` sets `vulnerabilityDataAvailable: false`. Large trees are queried in batches of 1,000 as OSV's budget allows, so a tree past 10,000 dependencies is answered in full, and a long answer is read to its last page. An advisory OSV matched whose record it then failed to return is listed as `details: "NOT CHECKED"`: its severity is unknown, not low, no `severity_filter` drops it, and it is asked for again on the next scan instead of being cached. The scan the other tools reuse is at most one hour old; past that it is taken again.

**Two grades for one advisory.** `severity` and `by_severity` are the grade the 4DA app presents, adjusted for scope (a transitive copy caps critical at high, a dev-only copy drops a level); the advisory's own grade is always visible beside it: `advisory_severity` on a package row whose own grade differs, and `by_advisory_severity` beside `by_severity` (the detailed answer also keeps it as `advisory_by_severity`). When any advisory is critical by its own grade, the `summary` says so first (after any NOT CHECKED headline): how many, on which package versions, and how many are presented lower because they are transitive or dev-only. Every recommendation names the own grade where it differs ("3 high (2 critical by the advisory)").

**What "osv-scanner parity" covers, and how it is measured.** Two things: reading the same installed packages out of a lockfile (inventory), and matching them to the same advisories (findings). It is not feature parity: osv-scanner reads ecosystems this server does not (Maven and Gradle among them). The measurement is the conformance corpus in the 4DA repository, fetched at a pinned commit: 36 cases (32 public repositories at pinned commits, 4 synthetic), scored for npm, crates.io, PyPI, Go, RubyGems and Packagist, with 3,929 OSV records pinned as OSV.dev served them (and 6 synthetic rule records). The expected inventory comes from osv-scanner 2.6.0 and the expected findings from OSV.dev's own evaluation of each installed version, with every correction recorded in the corpus; the corpus is kept by the same maintainers as this server. Against it this engine reads 20,458 inventory entries with none missing and none extra, and reports 4,785 findings with 0 false positives and 0 false negatives. That run is offline, on the pinned records, with this server's own range matcher: it measures the readers and the matching, not the live requests to OSV.dev, and not a lockfile damaged in a way the corpus does not hold. CI runs it on every change (`conformance (pinned)`) and a release requires it; to run it yourself: `node scripts/fetch-conformance.mjs && pnpm exec vitest run src/__tests__/conformance.test.ts --reporter=verbose`, which prints the table per ecosystem (see [conformance/README.md](conformance/README.md)).

Measured with a coding agent on the 6.2.5, 6.2.6, 6.2.7 and 6.5.1 release candidates (pre-registered, 49 dependency tasks x 3 trials, one model, `claude-sonnet-5-5`, tasks written by the authors, shell and web off in both arms): it wrote a vulnerable version in 82 of 138 well-posed runs without the server and 0 of 138 with it. The four runs share one recorded no-server arm and one truth pinned on 2026-10-24; the latest run came a month after that pin, and with the one task that has since become ill-posed set aside it reads 0 of 135 against 79 of 135. No result for the releases in between is published here. Harness, tasks, pinned truth and results: [`bench/g7`](bench/g7/).

- **OSV.dev** for known vulnerabilities, matched to exact installed versions
- **npm registry, crates.io, PyPI, Go module proxy** (registry.npmjs.org, crates.io and index.crates.io, pypi.org, proxy.golang.org) for versions, deprecations and yanks
- **npm download counts** (api.npmjs.org), for `dependency_health`'s weekly-downloads figure (`upgrade_planner` and `what_should_i_know` make the same request when they read registry data for npm packages), and for `dependency_check` when a new dependency's name is a near-miss of a popular package (that name and the popular one, nothing else)
- **The package's own registry archive** (registry.npmjs.org, static.crates.io, files.pythonhosted.org, proxy.golang.org) for the changelog `upgrade_impact` reads; GitHub only if you opt in with `FOURDA_GITHUB_CHANGELOG=true` (below)
- **npm full packument**, the **crates.io versions API**, the **PyPI JSON API** and the **Go proxy's version list** for `dependency_check` (publish times, yanks and retractions; on npm and crates.io also publishers, install scripts, per-version dependencies). These requests carry the package name only. Besides them, `dependency_check` requests per-release documents of the releases it is judging (`to`, a constraint's candidates, the safe releases it names): the Go proxy's `.info` and `.mod` (its list has no dates; the same requests `go get` makes, and `.mod` lists what the release requires), and on PyPI the release's own document (`pypi.org/pypi/<name>/<version>/json`, the only place a release that is not the latest lists its requirements); and it looks up, by name, the release lists of the packages those releases require (crates.io, PyPI) and their advisories at OSV.dev. The version you have installed (`from`) is named only to the Go proxy (its `.info`) and, on PyPI, only when it is also `to`. `upgrade_planner` names a version to a registry in two cases: on PyPI, a parent that uv.lock or a compiled requirements file names without its requirement is asked for by its own release (`pypi.org/pypi/<name>/<version>/json`, the installed version); and on npm, PyPI and Go a fix version is asked for by name. OSV.dev's advisory list for the package lets `dependency_check` name the safe releases in a constraint. Packuments are cached on disk and revalidated with `If-None-Match`; crates.io API reads are spaced one per second.
- **Hacker News Algolia API** (hn.algolia.com), only when you call `ecosystem_pulse`
- **GitHub** (api.github.com, raw.githubusercontent.com), only with `FOURDA_GITHUB_CHANGELOG=true`
- **Your embedding provider**, only if you configure one for semantic recall (a local Ollama URL, or api.openai.com; see below)

A redirect is followed only from a host to itself or to that host's own download hosts: crates.io to static.crates.io or index.crates.io, pypi.org to files.pythonhosted.org, proxy.golang.org to storage.googleapis.com, and GitHub (with `FOURDA_GITHUB_CHANGELOG=true`) to raw.githubusercontent.com, codeload.github.com or objects.githubusercontent.com. Those are all the hosts the server contacts.

Results are cached (24h for registry data, 1h for vulnerabilities, 30min for news) and rate-limited per source.

**What's sent over the network, and when:** nothing when your editor starts the server and lists its tools; the project is read locally, and the first request goes out when a tool that needs it is called (`vulnerability_scan`, `what_should_i_know`, `dependency_check` ...). Then: package names and versions (the same data visible in your lockfile), and, only for `ecosystem_pulse`, the names of a few of your dependencies as search terms. Never a private package's name (below). From a `what_should_i_know` task, the briefing sends a package name (with the version the task names for it) to its public registry and OSV.dev only when the project already depends on it in that same ecosystem (a Go module by its full path), when it is exactly a name on the server's bundled lists (popular npm and PyPI names, and names with a known malicious or hijacked release) for an ecosystem the project uses, a command in the task installs from, or a manifest file the task names, or when you declare it in `packages` with `public: true` (with the version you declare and the versions the task writes for it); a name is never looked up in any other ecosystem. A name you declare public is sent, so declare `public: false` for anything from a private registry, an index of its own, git or a path. As a courtesy, when the task holds one of a fixed list of source spellings (`--registry`, `--index-url`, pip's `-i` and `-f`, `--git`, `--path`, `registry=`, `npm_config_registry`, `PIP_INDEX_URL`, `UV_INDEX`, `GOPROXY`, `[[tool.uv.index]]`, `[[tool.poetry.source]]`, a Cargo `[registries]` or `[source.<name>]` table, a go.mod `replace`, and a few more the CHANGELOG lists), no name the task adds is looked up, declared public or not; a source named any other way ("from our Artifactory") is not noticed, and the project's own private rules still override a public declaration. Build metadata and a local version label (`+build7`) are never sent. No other text of the task is sent, and none of it goes to an embedding provider. A name you declare `public: false` or put in `not_packages`, and every other name of the task, is not looked up by the briefing: it waits in `task_packages.to_confirm` until you answer for it. A declaration does not change the project's own vulnerability scan, which reads the installed dependencies and sends their names unless the project's configuration marks them private (`FOURDA_PRIVATE_PACKAGES`, an `.npmrc` scope or registry, a pip index, `GOPRIVATE`): mark an installed private package there. A credential in the task (a token shape, a UUID, a password shape, the value of a TOKEN, KEY, SECRET or PASSWORD setting, a high-entropy word, twelve or more hex digits, a word with a shell expansion in it, a setting such as `password==hunter2` whose value is no version (shown only as its name), a word with a colon inside), a URL's user info, an option's value, a shell variable, a git remote and an email address are never read as names, and a package the task's own command takes from a private registry, git or a path is not looked up, even when declared public; such words are named in `task_packages.not_read` without their value. A credential that looks like an ordinary word can appear in `to_confirm`; nothing about it is sent unless you declare it public. No source code, no file paths, no personal data. The call-site scan of `upgrade_impact` runs locally. Set `FOURDA_OFFLINE=true` to disable all network calls.

**Private packages are never sent.** A package is private, with nothing to configure, when your machine already says so:

- **npm:** its scope is mapped to a registry other than the public one in the project's `.npmrc` (or a parent directory's, or any member directory's the project walk finds, lockfile or not), your user `.npmrc` (or `npm_config_userconfig` in any case), the global npmrc (`npm_config_globalconfig`, else `<prefix>/etc/npmrc` with the prefix from `npm_config_prefix` / `PREFIX`, `%APPDATA%\npm` or node's own), a quoted key (`"@acme:registry"=...`), the environment (`npm_config_@acme:registry`, any case), `.yarnrc.yml` `npmScopes` at any indentation or in flow style (`@acme:registry=https://npm.acme.dev/`; the project's and those above it, `~/.yarnrc.yml`, under the name `YARN_RC_FILENAME` gives, and `YARN_NPM_SCOPES`), or `bunfig.toml` `[install.scopes]` (a URL, `{ url = ... }`, or an `[install.scopes.<scope>]` table; the project's, `~/.bunfig.toml` or `$XDG_CONFIG_HOME/.bunfig.toml`); or your lockfile installs it from another host: the `resolved` location in `package-lock.json` / `npm-shrinkwrap.json` and yarn v1 `yarn.lock`, a yarn berry `resolution` URL (or `__archiveUrl`), the `tarball` in `pnpm-lock.yaml` (GitHub Packages included), the registry URL of a `bun.lock` entry. A default registry that is not public (`registry=` in any of those `.npmrc` files, `npm_config_registry`, yarn's `npmRegistryServer` or `YARN_NPM_REGISTRY_SERVER`, bun's `[install] registry`) makes every npm package of the project private (see "Mirrors" below); registry.npmjs.org, registry.yarnpkg.com and registry.npmmirror.com are public.
- **Go:** its module path matches `GOPRIVATE`, `GONOPROXY` or `GONOSUMDB`, from the environment or from `go env -w` (the `GOENV` file; as go does, an empty variable falls back to it), whatever spelling a tool is given (`https://github.com/acme/mod.git`, `git+ssh://git@github.com/acme/mod`, `git@github.com:acme/mod.git`, `...#v1.2.3`, `.../tree/main`); or `GOPROXY` names a proxy that is not public (see "Mirrors" below).
- **Cargo:** `Cargo.lock` installs it from a registry other than crates.io, or from git (path dependencies are local code and were never sent); or `Cargo.toml` (the root's and every workspace member's, `members` globs and `exclude` respected) takes it from another registry (`registry = "acme"` other than `crates-io`, or `registry-index`) or from git, in any dependency table or `[patch]`, with or without a lockfile; or a `.cargo/config.toml` (in the project, any directory above it, or `CARGO_HOME`) patches it from git or another registry, or replaces crates.io with a registry that is not crates.io (see "Mirrors" below; a vendored directory is crates.io's own crates).
- **PyPI:** `uv.lock`, `poetry.lock` or `Pipfile.lock` installs it from an index other than pypi.org; or a requirements file pins it under `--index-url` / `-i` naming another index (set in the file or in any file it includes with `-r` or `-c`, nested); or `pyproject.toml` takes it from another index (uv `[tool.uv.sources] name = { index = "acme" }` naming a `[[tool.uv.index]]` that is not pypi.org; Poetry `name = { version = ..., source = "acme" }` naming a `[[tool.poetry.source]]` that is not pypi.org), with or without a lockfile; or a direct reference installs it from a location that is not public (`name @ https://pkgs.acme.dev/...`, `name @ git+https://git.acme.dev/...`, `name @ file:...`, uv or Poetry `git` / `url` / `path` sources; pypi.org's files, the public wheel indexes and GitHub, GitLab and Bitbucket are public); or, with no lockfile, uv, Poetry or PDM consults an index that is not pypi.org for any name (a `[[tool.uv.index]]` that is the default or not `explicit`, `[tool.uv]` `index-url` / `extra-index-url`, `uv.toml` in the project or above it, the user's or the system's, `UV_DEFAULT_INDEX`, `UV_INDEX_URL`, `UV_INDEX`, `UV_EXTRA_INDEX_URL`, a Poetry source that is not `priority = "explicit"`, a PDM source): then every package the project declares is private; or pip is configured with another index (`PIP_INDEX_URL`, or `index-url` in any pip config file pip reads: site-wide `%ProgramData%\pip\pip.ini`, `/etc/pip.conf`, `$XDG_CONFIG_DIRS/pip/pip.conf`, `/Library/Application Support/pip/pip.conf`; per-user `%USERPROFILE%\pip\pip.ini`, `%APPDATA%\pip\pip.ini`, `~/.pip/pip.conf`, `~/.config/pip/pip.conf`, `~/Library/Application Support/pip/pip.conf`; the virtualenv's `$VIRTUAL_ENV/pip.ini` or `pip.conf`; `PIP_CONFIG_FILE`) and a requirements file installs it. A company mirror of PyPI named there counts as private too: list nothing, and its packages are reported as not checked. An `--extra-index-url` (in a requirements file, `PIP_EXTRA_INDEX_URL` or pip config) that is not pypi.org counts the same way: pip takes each package from whichever index has the newest release, so any name it installs may come from that index, and the packages a requirements file installs are private (not sent, reported as not checked); the answer names the index (`registry_notice`). A lockfile that records each package's index (`uv.lock`, `poetry.lock`, `Pipfile.lock`) lets the public ones be checked.
- **RubyGems:** `Gemfile.lock` lists it under a `GEM` section that names a `remote:` other than rubygems.org (every gem of such a section is private, whatever other remote it names).
- **Packagist:** `composer.lock` installs it from a host other than Packagist and the public code hosts (a Satis or Private Packagist server), or from a repository `composer.json` declares that is not Packagist (`vcs`, even on GitHub; `composer`; `path`; `artifact`).

**Mirrors: one policy for every ecosystem.** A registry, index or proxy that is not the public one, and that the package manager consults for any name (an `.npmrc` `registry=`, a pip `--index-url` or extra index, a uv or Poetry default index, `GOPROXY`, a Cargo source replacement), can serve packages published nowhere else, so every package of that ecosystem the project installs is private: never sent, reported as not checked, with the reason and the setting named (`registry_notice` for npm and pip). If such a server only mirrors the public registry (Artifactory, Nexus, devpi, Athens as a pure proxy), say so with `FOURDA_PUBLIC_MIRRORS=artifactory.acme.dev,athens.acme.dev` (hosts, comma- or space-separated) and its packages are checked again; its lockfile hosts count as public too. Until 6.3.0 an npm `registry=` host and `GOPROXY` were read as mirrors and unscoped names were sent. Go needs no proxy for a module on your own host: one that neither `GOPRIVATE` (or `GONOPROXY` / `GONOSUMDB`) names nor a private `GOPROXY` covers is fetched by go through the public proxy too, and is looked up here the same way; name it in `GOPRIVATE`.

A dependency taken from a path, git or a URL is not the registry package of its name, and is never looked up by that name, in the manifests and lockfiles the scan reads. npm specs are read as npm reads them: `file:`, `link:`, `workspace:`, a bare path (`../libs/x`, `./x`, `~/x`, `/opt/x`, `C:\x`), a tarball file (`vendor/x-1.0.0.tgz`), GitHub shorthand (`org/repo#ref`) or any git spelling, a URL other than the public registry's own tarball of that package, another protocol, an alias npm refuses, and a protocol spelling with whitespace around it; so is a dependency an override forces to one of those (`overrides`, `resolutions`, `pnpm.overrides`), a name the lockfile installs only as a link (a workspace member), from git, a URL or a local archive, and a workspace member's own name, read from the enclosing workspace root whether or not a lockfile exists. A `catalog:` dependency is what its pnpm or Bun catalog entry says, judged by the same rules; one whose entry cannot be found or read is withheld. Cargo: `path` and `git` crates, a crate a member inherits with `{ workspace = true }` (or `name.workspace = true`) from such an entry, the dotted forms (`name.path = ...`, `name.git = ...`, `"name".path = ...`), and both the key and the package of a `package =` rename. Python: a requirement installed from a local path, editable or archive, a git checkout anywhere (GitHub included), an archive URL on a host other than PyPI's own file host, a uv `{ workspace = true }` source, and the project's own `[project]` or Poetry name. A requirement given as a URL on PyPI's own file host (`six @ https://files.pythonhosted.org/...`) is not withheld: `dependency_check` checks it by name, while the scan lists it under `not_checkable` (no version is read from the URL). npm workspace members linked by a symlink or junction count as members, and a server started in a folder with no manifest below a project, below a folder that holds `.git` (a `.git` file counts; `GIT_DIR` is not read) (`src/lib`, `src/bin`; at most three levels, never above that folder) reads that project, so the first call there does that project's scan; with no `.git` above it, nothing above the start folder is read. Such a dependency gets no registry row in `dependency_health` or `upgrade_planner`, `dependency_check` answers it `unknown` with `not_checked: "private"`, `upgrade_impact` refuses it, and neither the briefing nor `ecosystem_pulse` sends it; what it installs is listed under `coverage.not_checkable`. Such a name is also withheld when you ask about it for another project, while a scanned project still declares it so, unless the project you ask about itself declares it as a registry dependency; an alias key is withheld only inside the project that aliases it. The answer says `NOT CHECKED (not a registry release)` and where the name comes from. 6.5.0 and earlier sent many of these names by themselves: `dependency_health` and `upgrade_planner` asked the registry about them, `ecosystem_pulse` sent them to Hacker News, and `dependency_check`, `upgrade_impact` and the briefing looked them up when asked. Versions, ranges, dist-tags (`latest`, `next`), a catalog entry that is a range and an `npm:` alias's target are registry releases and are checked; inside the project whose `package.json` declares an alias, its own key is never sent, with any lockfile, and asked about directly it is answered with its target named; in another project the same word is an ordinary package name and is looked up as one (a key such as `lodash` or `@types/react` is also a real public package). Not covered: a manifest the scan does not read (a project in a subdirectory with no lockfile, which the scan lists under `manifests_without_lockfile`), so a name declared only there is looked up if you ask about it directly; the project's own root package name in npm, pnpm, Yarn v1 and Bun, when you ask about it directly; a crate in a folder the Cargo workspace `exclude`s that nothing depends on, asked about directly; a Go module replaced by a `GOPRIVATE` fork, asked about directly, is looked up by its original path; and the repository path of an npm git dependency, asked about as a Go module, is looked up as one; an alias only the lockfile records (a `package-lock.json` root that still lists `"x": "npm:y@1"` after `package.json` dropped it, a lockfile out of step with its manifest) has its key sent when that package is found vulnerable, as in 6.5.0; for `npm:npm:x@1` and `npm:x-1.0.0.tgz`, x is looked up if asked about directly; and an alias whose range npm cannot read (`npm:x@=~7`, `npm:x@1.0.0 junk`) is read as an alias to x, and x is sent like any alias target. A package a `workspaces` pattern excludes (`!packages/legacy`) is not a member, so npm installs it from the registry, and it is checked as a registry dependency.

Names are compared the way each registry compares them: a crate is the same whatever its case and whether it is written with `_` or `-` (`acme_core`, `Acme-Core`), PyPI names are PEP 503-normalised, npm, RubyGems and Packagist names are case-insensitive. Look-alike spellings are folded first (NFKC, so fullwidth `＠acme／ui` is `@acme/ui`; every Unicode dash or hyphen is `-`), and `acme/ui` or `github:acme/ui` is read as a form of `@acme/ui`.

Add your own with `FOURDA_PRIVATE_PACKAGES`: comma- or space-separated globs, `*` matching anything (`/` included), each optionally prefixed with its ecosystem: `FOURDA_PRIVATE_PACKAGES="npm:@acme/*, crates.io:acme-*, PyPI:acme-*, Go:github.com/acme/*"`. A bare scope (`@acme`) covers the whole scope; PyPI names are compared PEP 503-normalised (`Acme_Auth` is `acme-auth`). The rules are read again whenever one of those files or variables changes. A name your project also installs from the public registry is public (asking about it reveals nothing). A private package is still read from your lockfiles, and is never looked up anywhere, as itself or as the parent of a public one: `vulnerability_scan`, `dependency_health`, `upgrade_planner` and `what_should_i_know` lead with `NOT CHECKED (private)` (the briefing also for a private package the task only names, installed or not, and never calls such a task `safe_to_delegate`) and list each one with the file or setting that made it private (`coverage.private_dependency_list`), so the answer is never a clean one for it; `dependency_check` answers it `unknown` with `not_checked: "private"` (a name withheld only because a lockfile or manifest of the project could not be read is said as that, `NOT CHECKED (unreadable lockfile)` with `unreadable_file`, and the remedy is to repair the file); `upgrade_impact` refuses it; `upgrade_planner` never looks up a private parent's releases, and a step that arrives through one leads with `NOT CHECKED (private)` and names it in `privateParents` (never an inferred refresh); `ecosystem_pulse` never uses its name as a search term (its terms come only from the project the server runs for, never from other projects in the same data folder, and a name another of those projects installs privately is never one). As a second line of defence, every OSV.dev, registry and search request passes one check that refuses it when its URL or body names a private package; a refused request reads as not checked, never clean. Registry URLs are shown without credentials.

**GitHub release notes (opt-in, off by default).** Many packages ship no changelog in their registry archive (vite, zod, cobra, most Go modules). With `FOURDA_GITHUB_CHANGELOG=true` in the server's environment, `upgrade_impact` reads the repository's GitHub releases when the archive has no changelog for the range (for PyPI, first a changelog file the project links on GitHub from its `project_urls`). GitHub then receives the repository name and the versions, nothing else. It uses the unauthenticated REST API (60 requests an hour) or `GITHUB_TOKEN` when set (5,000); a rate limit is reported with its reset time, never retried in a loop, and results are cached. With it off, an answer without a changelog says so and names the setting; nothing is guessed.

**What's written to disk, and where:** only files the server owns, in its folder in your user data directory (`%LOCALAPPDATA%\4da-mcp`, `~/Library/Application Support/4da-mcp` or `~/.local/share/4da-mcp`; `FOURDA_MCP_HOME` moves it): `cache.db` (registry, OSV and changelog responses, in every mode; safe to delete, it costs refetches only), `standalone.db` (without the desktop app: your project scan and the decisions, agent memory and feedback you record; no cache) and `check-ledger.jsonl` (each `dependency_check` verdict, for the plugin hook; started empty when the server starts serving; moved to `check-ledger.1.jsonl` past 512 KB, so the two hold about 1 MB at most). Nothing is written inside your repository. Once per process the server creates and removes an empty `.write-check-<pid>-<ms>.tmp` and `.write-check-<pid>-<ms>.db` in that folder to learn whether it can write there; a folder it cannot write is said plainly ("the data folder <dir> is not writable"), the cache is then kept in memory, and a folder made writable later is used after a restart. A `cache.db` another process holds locked is set aside for 30 s, the cache kept in memory meanwhile. `standalone.db` is known by its path: a file there that a killed first start left empty or half-made is completed in place, and a table that exists is never touched. (Until 6.3.0 standalone mode kept the cache inside `standalone.db`; that table is dropped the first time 6.3.0 opens it.)

When the 4DA desktop app is installed, the server reads the app's database (`4da.db`) through a **read-only** connection and never creates or alters anything in it: no tables, no columns, no cache. It is never the dependency inventory either, and a scan never writes to it: the dependency tools read every lockfile under the project root from disk, exactly as without the app, with the same `coverage` (see "Standalone vs. Full Mode"). The only writes are rows in the four app-owned tables the tools exist to fill, so the app sees them: decisions (`decision_memory` -> `developer_decisions`), agent memory (`agent_memory`), and feedback (`record_feedback` -> `interactions` and `feedback`, which the app's calibration reads). Those go through a separate write connection that waits briefly for the app's lock. If your app version lacks the table or a column a record needs, the record goes to `standalone.db` instead and the response says so in `_meta`. (Before 6.1 the server also created a `live_cache` table inside the app's database; it now keeps that cache in `cache.db`.)

**Where configuration and the database come from:** `FOURDA_DB_PATH` if set, else the desktop app's database in its data directory, else the server's own `standalone.db`. `FOURDA_DB_PATH` must name an existing file (a relative path resolves against the server's working directory); one that names no file is refused and nothing is created there, except when it names the server's own `standalone.db`. A file with no tables is not taken for the app's database either. Then the tools that answer from the project's files (`vulnerability_scan`, `dependency_health`, `dependency_check`, `upgrade_impact`, `upgrade_planner`, `what_should_i_know`, `ecosystem_pulse`) still answer, each answer carrying `_meta.database_note` with the reason (the briefing has no stored decisions, memories or feed rows, and says so in `stored_data_note`); every other tool returns the error, which names the path. A database of this server's own format at a path other than its own `standalone.db`, and an app database that has not finished setting up (before the app's first migration), are not used either: the server changes nothing in that file, runs every tool on its own `standalone.db` (so the tools that need the desktop app are not offered), and says why in `_meta.database_note`, on stderr and in `--doctor`. A fresh clone whose committed `.mcp.json` names `./data/4da.db` therefore still gets dependency answers. Embedding settings come from `FOURDA_SETTINGS_PATH`, else the `settings.json` beside `FOURDA_DB_PATH`, else the desktop app's data directory. Nothing is picked up from the directory the server is started in: until 6.2.5 a `data/settings.json` or `data/4da.db` inside (or beside) the working directory was adopted, so a cloned repository could redirect semantic recall to a host of its choosing or plant "decisions".

> The one exception: if you *explicitly* configure an OpenAI embedding provider (`FOURDA_EMBED_PROVIDER=openai`) for semantic recall, OpenAI receives exactly this, to be embedded: the text of the decisions and memories you stored (subject, decision or content, rationale, rejected alternatives), and the text being searched for: an `agent_memory` recall query, or a `check_decision_alignment` technology and pattern. `what_should_i_know` sends it nothing: it ranks your decisions and memories on this machine. Never the file paths you pass in `files` (they rank results locally), never source code. The default — no embedding provider, or a local Ollama one — keeps everything on your machine, and `FOURDA_OFFLINE=true` overrides it regardless.

**Ecosystems supported:** npm, crates.io (Rust), PyPI (Python), Go; `vulnerability_scan` also reads RubyGems (`Gemfile.lock`) and Packagist (`composer.lock`). Maven, Gradle and .NET are not read, and are listed as not covered. `upgrade_impact` reads npm, crates.io, PyPI and Go. PyPI: versions and dates from the PyPI JSON API, the changelog from the release's sdist, and import sites matched on the module the distribution installs: read from your virtualenv's metadata (`.venv`, `venv`, `env`: `top_level.txt` or `RECORD`), else a table of well-known differences (`PyYAML` -> `yaml`, `Pillow` -> `PIL`), else the distribution name, which the answer then labels an assumption. Go: versions and dates from proxy.golang.org, the changelog from the module zip, and a major version 2+ reported as the module path change it is (`github.com/jackc/pgx/v4` -> `/v5`), with the files that import the old path. `dependency_check` reads all four too; on PyPI and Go, where the registry exposes no publisher identity or install hooks, those signals say "not applicable".

**Known limits, stated plainly:** a `requirements.txt` without a lockfile names only your direct pins, so their transitive dependencies are not scanned (use `uv lock`, `poetry lock` or `pip-compile`). Many packages ship no changelog in their registry archive (fastembed, vite, zod among them); `upgrade_impact` then says so and gives the release-notes URL instead of guessing. Breaking entries are flagged from the changelog's headings and wording, and every entry carries the heading it sits under (`under`). Measured on a panel of 40 real upgrades across npm, crates.io, PyPI and Go (1,618 entries; gold is the majority of three blind raters, each a model instance working to a written rubric, with a verbatim quote for every label; the panel and the measurement are in the test suite): on the 20 upgrades held out from rule-making, 95% of entries flagged breaking were breaking (95% CI 89-98%) and about 72% of breaking entries were flagged; Go release notes written as prose are the weakest (about 54% recall). Treat the flags as a pre-sort: read every entry of a major upgrade. Each answer says this in `_meta.classification`.

The plan has limits of its own. `run_order` is the part of the plan that is safe to run as commands. Rows that need a hand edit (an override that crosses a major of what its parents declare, Yarn classic lockfile entries with copies on several release lines, a requirement edit the manager has no command for) are counted and named in `run_order_note`; running the script alone does not finish them. Measured for 6.5.0 on 14 public projects (`bench/plan-exec`: each project's plan run top to bottom on a copy, then rescanned), the script ran 0 failing steps where 6.4.0's plan had 10, and on Yarn classic projects it leaves most of the work as named hand steps. A target is checked for vulnerable dependencies it holds one level down and, on npm, for the exact pins of those dependencies two levels down (`@hey-api/openapi-ts` 0.97.3 pins `@hey-api/json-schema-ref-parser` 1.4.2, which pins an affected `js-yaml` 4.1.1: the plan says so and gives no command for it, and `dependency_check` names the copy); a range two levels down, anything deeper, and a copy bundled inside the target's tarball (`tap` bundling its own copies) are not detected. A first plan or check of many crates can need a second call: crates.io allows one request a second, so a cold batch of 25 crates may not finish within one call's time, and what it did not reach is answered NOT CHECKED, never clean (the lookups run on, and the next call answers from them). With `project_path: "*"`, the app's plan has one step per package, which can still cover copies whose routes differ between projects; `upgrade_planner` for one project gives each copy its own row. A step can still fail on what the plan could not read, and the package manager's resolver picks the copies no step names: check each step's result before running the next (its `if_it_fails` says how to put back what it changed), and scan again after the run, as `after_run` says.

## Tools

### Dependency Security

| Tool | What it does |
|------|-------------|
| `upgrade_impact` | What changes between the installed and a target version of one dependency (npm, crates.io, PyPI, Go): releases in between, changelog entries classified breaking / deprecation / security, the breaking ones that touch your code (symbols you import, and route or pattern syntax in your string literals, e.g. axum 0.8's `/:id` -> `/{id}`), the files that import it, advisories fixed. |
| `vulnerability_scan` | Every installed copy in every lockfile matched against OSV.dev. Scope-adjusted `severity` with the advisory's own grade beside it (`advisory_severity`, `by_advisory_severity`; see "Two grades for one advisory"), an upgrade target checked against every advisory of the package (the highest per-advisory fix can itself be affected by another), where each version is pinned, and a `coverage` block on every answer (`complete: true` with `lockfiles_read` when nothing was left out, `complete: false` with what was left out otherwise). Rows come in one fixed order, so detailed pages never lose or repeat a row. Concise by default (one row per vulnerable package version, the 40 most severe; about 10k tokens on a project with about 290 advisories); `package` for one dependency; `response_format: "detailed"` for every advisory. |
| `dependency_health` | Version freshness, deprecation (of the version you run) and vulnerability counts per dependency. With no lockfile read it withholds the score (`healthScore: null`, `withheldReason: "no_lockfile"`), and so it does when a lockfile was read only in part (older than its manifest, cut short, entries skipped) or disagrees with the one read (`withheldReason: "lockfile_partial"`, the summary led by NOT CHECKED and what was not read). After a directory walk that stopped early it leads with NOT CHECKED and scores only the part that was read. |
| `upgrade_planner` | The smallest version no advisory affects for each vulnerable package, majors flagged (a 0.x minor counts as a major). Direct steps (`upgrade_direct`) carry `upgradeCommands`, the command per declaring project directory, keeping how the dependency is declared (`npm install x@v --save-exact` for an exact pin, `npm install "x@^v"`, `pnpm up`, `yarn upgrade` / `yarn up`, `cargo add` with `--dev` / `--build` / `--target` / `--rename`, `go get`; none for a `>=` / `||` / tag / git spec or a yarn workspace member), and a direct target is raised when a slightly newer release also clears a vulnerable transitive it pins. Transitive fixes: `lockfile_refresh` with the exact command (`npm update`, `pnpm update`, `yarn up -R`, `cargo update -p ... --precise`) when every parent's declared requirement already admits a clean version; `upgrade_parent` when a parent pins it but a newer release of that parent admits one, with `parentUpgrades` naming the smallest such release that is itself clear of the parent's advisories (read from the registry), the declared dependencies to bump (`levers`, with their commands; none when the lockfile cannot tie the parent to a declaration) and, when the new requirement still admits the installed copy, the refresh to run after the install (`refreshCommands`); `override_or_replace` with the override syntax (npm `overrides`, pnpm `pnpm.overrides`, yarn `resolutions`, Cargo `[patch]`) when the parent will not move (deprecated, already its latest release, or no release admits a clean version); `waiting_on_upstream` when the parent's releases could not be read, and for a copy bundled inside its owner's package, which only a new owner release (or replacing the owner) can move. `waiting_on_upstream` means no command you can run today fixes that copy; a Python parent the project does not declare is moved by its own refresh (`uv lock --upgrade-package <parent>`) when what requires it admits a release of it that admits the fix. When one version is installed both bundled inside another package and on its own, the row is the `lockfile_refresh` for the copies that are not bundled and `bundledCopies` names each owner whose bundled copy stays; the summary counts that row as a refresh and as waiting on upstream, never as fully fixed. A Cargo upgrade into a release that no longer offers a feature your `Cargo.toml` enables is an instruction naming the feature, not a command cargo would refuse (`upgrade_impact` lists such features in `your_code.cargo_features_removed`). Every row carries `commands` (`{ dir, run }`, `dir` relative to the project, `"."` for the root; empty when its reasons say why nothing is run, such as a hand edit of a lockfile entry or a manifest; a direct upgrade with no command always says why in its reasons, and a freshness upgrade, which no advisory against the installed version makes a security fix, says so, is left out of `run_order` and names the hand step that takes it), and the plan carries `run_order`: the rows shown as one script (`{ n, dir, run, fixes }`) that is safe to run from the first step to the last: one version-setting command per package per directory at the highest release any row needs, nothing set below a version that is installed or that an earlier step sets, every `go get` of one module directory in one command, upgrades before in-range refreshes and a parent upgrade before the refreshes that follow it, and a target that breaks an installed package's peer range run in one command with that package's release when the plan moves it, or left out with the reason. On pnpm the peer step after a parent's upgrade names the release that upgrade leaves, never a lower one. An override within its parents' major is written as commands (`npm pkg set "overrides.<name>=<version>"`, or `pnpm.overrides` / `resolutions`, then the install, in the lockfile's directory), and on Yarn classic a package the lockfile holds on one release line, every copy at or below the target, is refreshed with an exact resolution (`npm pkg set "resolutions.<name>=<target>"`, then `yarn install`; the resolution stays). In a uv workspace each command runs once, at the root, and a copy only a member's leftover `uv.lock` lists is a hand step (delete the file); a uv pin whose release needs a newer Python than the project supports is a hand step that says to raise `requires-python` first; a Cargo row whose release needs a newer Rust than the `rust-version` its `Cargo.toml` declares (inherited from `[workspace.package]` too) carries `needsNewerRust` (`{ crate, version, needs, declared, manifest }`) and a reason, and the step stays, since `cargo update --precise` and `cargo add` install it anyway and only the build on the declared Rust fails (the summary and `run_order_note` count such rows); a package a uv, npm/pnpm/Yarn or Cargo workspace member defines is taken from the workspace and never upgraded from the registry. `run_order_note` says what it covers and what it leaves out, and why, and counts and names the rows that are hand edits and not in the script. ### Confirming packages

The briefing never guesses whether a word of a task is a public package. In a clean npm project a first call without `packages`

```
what_should_i_know { "task": "npm install lodahs" }
```

answers `confirmation_needed`, with `"to_confirm": [{ "name": "lodahs", "ecosystems": ["npm"], "seen": "operand of an install command", "hint": "one edit from lodash: if you mean lodash, confirm lodash instead" }]` and a `next_step`. The agent says what it means:

```
what_should_i_know { "task": "npm install lodahs", "packages": [{ "ecosystem": "npm", "name": "lodahs", "public": true }] }
```

lodahs is checked in that call (`"checked": [{ "name": "lodahs", "ecosystem": "npm", "version": "0.0.1-security", "verdict": "avoid", "basis": "confirmed public by you" }]`), the level is `human_only` (npm took lodahs down as malware), and the `avoid` is in the check ledger, so the guard hook holds `npm install lodahs` as well. Had the agent meant lodash, it would have declared lodash. An agent that knows its packages passes them on the first call and gets the whole briefing at once.

A command written inside a sentence is read to the end of that sentence: "Use npm install msw for tests" holds msw, for and tests, and each waits like any operand. Putting for and tests in `not_packages` keeps the level at `review_needed`, since they stand where a package stands, and the reason adds that for a clean answer the agent may also pass the command on its own line or in a code span, with only package names after the verb, keeping the user's words as the request. Written on its own line, in a code span (`` `npm install msw` ``) or in parentheses ("(npm install msw)"), the command holds only msw.

## The guard hook

The Claude Code plugin adds a hook that runs before every edit and command an agent makes (PreToolUse on Edit, MultiEdit, Write, NotebookEdit, Bash and PowerShell). It is a guard-rail against an agent's mistakes and shortcuts: it stops an agent from writing or installing a dependency version that has not been checked. It is not a sandbox. An agent that sets out to get around it can (a script file that runs the install, a path built from pieces), and it says nothing about what a package does once it is installed. It is plain Node, reads no network and contacts nothing.

**How a version is cleared.** Every `dependency_check` answer for an item it accepted is recorded in a ledger in the server's data folder (`check-ledger.jsonl`, never sent anywhere), and so is the answer for every package a `what_should_i_know` call declared `public: true` and checked (a task that holds one of the listed source spellings records nothing). The hook reads the answers of the last 24 hours, for the exact version the edit or command writes:

- `proceed` or `review`: the call goes ahead.
- `avoid` or `wait`: it is held, with that answer's reason.
- No answer, or only `unknown`: it is held, and the denial gives the exact `dependency_check` call to make; the same edit or command goes ahead once that call answers `proceed` or `review`.
- A package named without a version (`npm install x`, `pip install x`, `cargo add x`, `go get x`, `cargo install x`, `yarn global add x`) installs the newest release, so it needs an answer for `latest` (`to: "latest"`). With npm, pnpm, Yarn, Bun, `uv add`, `poetry add` and `cargo add`, a name alone goes ahead on that answer only where the hook has placed the install: every change of folder before it in the call is one it follows to a folder that exists (cd, pushd, Set-Location, Push-Location, Git Bash `/c/...` paths; not `~`, `-`, popd, a variable, a pipeline, or past the end of a subshell) and every directory option (`--prefix`, `-C`, `--dir`, `--cwd`, `--directory`, `--project`, `--manifest-path`) resolves the same way; no workspace option is on it (`-w`, `--workspace`, `--filter`, `-F`, `-r`, `-p`, `--package`, `yarn workspace`); no folder from there up to 12 levels above is a workspace root of its ecosystem (a `pnpm-workspace.yaml`, a `package.json` with `workspaces`, `[tool.uv.workspace]`, a Cargo `[workspace]`) or holds a `go.work`; and no project file there or above mentions the name (in a `package.json`, its scripts, description, keywords and the like do not count). Otherwise it is held with the cause and asks for the version (`x@1.2.3`, `x==1.2.3`): every name alone inside a workspace is held, because the manager may reuse a release another member has. With npm, pnpm, Yarn and Bun, `x@latest` is judged at the newest release even beside a declared version, which those managers replace. A dist-tag other than `latest` (`x@next`) or a Go branch is held until the command names the version.
- A range or constraint needs an answer for that same constraint, or a `proceed` or `review` for exactly the release its inclusive ceiling names (`<=1.2.3`, `1.0.0 - 1.2.3`, with only lower bounds beside it and no `!=`); a lockfile that already holds a release in the range keeps that one, so check the locked release too. `"latest"` in `package.json` needs an answer for `latest`.

Marking a package `public: false` in `what_should_i_know` records nothing and releases nothing. A package from a private registry is released by a private-registry rule the server reads (`FOURDA_PRIVATE_PACKAGES`, an `.npmrc` scope or registry, `.yarnrc.yml` `npmScopes` or `npmRegistryServer`, `bunfig.toml`, `GOPRIVATE`, `GONOPROXY` or `GONOSUMDB`, `GOPROXY`, a Cargo source replacement, a pip, uv or Poetry index, a requirements `--index-url`, a Pipfile source): `dependency_check` then sends nothing, records the name private, and any version of it goes ahead, in any project, for 24 hours, unless an `avoid` or `wait` for that exact version or constraint came first. A name a project takes from git, a path, its workspace, an alias, a catalog or another registry is not looked up either, and is held when a command or an edit would install it from the public registry instead: that release was not checked, and the denial says how to go through. A name the server withheld because a lockfile could not be read is held, with the file to repair.

**What it reads.** An edit made with the Edit, MultiEdit or Write tool to `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, `pnpm-workspace.yaml` or a requirements file (`requirements*.txt`, or any `.txt` in a folder named `requirements`), the name matched whatever its letter case: only dependency declarations count, never a comment or a description, and each section is compared on its own. A declaration that bounds nothing by its meaning (`*`, `""`, `x`, `x.x`, `*.*`, `=*`, `^*`, `v*`, any `||` alternative that is empty or only wildcards, a name alone in a requirements file or a pyproject array, the same wildcards in Poetry and in every Cargo form (`"x"`, `{ version = "x" }`, `[dependencies.x]`, target and workspace tables)) needs an answer for `latest`; a dist-tag other than `latest` is held until it names a version. pnpm's `packageExtensions` are read as declarations, and a change under a `pnpm-workspace.yaml` key the hook neither reads (catalog, catalogs, overrides, packageExtensions, configDependencies) nor knows to install nothing is held. `package.yaml` and `package.json5`, which pnpm reads as manifests, are held with the advice to write the manifest as `package.json`, whatever their spelling (`package.yaml::$DATA`, a trailing dot or space); a NotebookEdit of any manifest is held with the advice to use Edit or Write. A `go.work` is read for its `replace` directives as `go.mod` is. A command: any line in which a package manager's name (npm, pnpm, Yarn, Bun, pip or `python -m pip`, uv, Poetry, Cargo, Go) is followed by one of its words that can add or move a dependency (install, add, up, update, upgrade, link, get, sync, lock, `npm pkg set`, `go mod edit`), also when it runs inside `bash -c`, `pwsh -Command`, `eval`, `npx`, `pnpm dlx`, `uv run`, `poetry run`, corepack and the other wrappers (at most three deep), after `sudo`, `env`, `timeout` and the like, or inside a subshell or a group.

**It lets such a command through only when it reads it whole.** A command it cannot read whole is held, and the denial names the first part it did not read and how to run the command so that it can: "Run the same command without `<that part>`", or with that part written out (a variable's value, an exact version); an option is named alone ("without the option `--before`; if that option takes a value, remove its value too"). Held this way, among others: a variable or a substitution on the line (`npm i $PKG`, `cd "$HOME/app" && npm i x@1`), beside a named package, every option that is not on that package manager's allow list (the list holds placement such as `--save-dev`, `-g` and `-w`, output, `--ignore-scripts`, `--dry-run` and a few more that cannot change which release is installed or where it comes from; `--before`, `--tag`, `--offline`, `--frozen-lockfile`, `--force` and an abbreviated option are not on it), a constraints file beside a named package, a version spec outside its registry's grammar, a package manager's own setting named anywhere at or before the install (`npm_config_registry=...`, `PIP_INDEX_URL=...`, `GOPROXY=...`), `xargs`, an alias or a function beside a package manager's name, a blank or control character other than a plain space or tab on an install line, `sed`, `awk` or `make` with an install on their line, and a PowerShell comma list. Text that only mentions an install goes ahead: `echo`, `grep`, `git commit -m "..."`, `gh pr comment`, a README written with the Write tool.

**Goes ahead without a verdict.** A command that names no package (`npm install`, `npm ci`, `pip install -r requirements.txt`): it installs the lockfile or the manifest's own ranges, and what the package manager chooses then is not checked. A package from a path or git. A package installed with exactly one option that replaces the public index (`--registry`, `-i`, `--index-url`, `--default-index`, Cargo's `--index`) and names a host that is private by its shape (localhost, a name with no dot, a name ending in .internal, .local, .lan, .corp, .home.arpa, .test, .example, .invalid or .localhost, or a loopback, private or link-local address), which the hook takes as the project's own source and does not judge; a package from any other host, and a URL or tarball on one, is judged on the ledger like a registry name, and the denial says how to mark a private name (`FOURDA_PRIVATE_PACKAGES`). Every other index or source option beside a named package is held (`--extra-index-url`, `--find-links`, `--no-index`, two sources). pnpm's `--registry` is read as npm's. A denial for an index, registry or source option never says to leave it out (that would fetch a private package from the public registry); it says how the hook reads the source and how to mark a private name. A requirements file is read when it is written with the Edit, MultiEdit or Write tool, not when it is installed.

**The ledger is the server's.** Any call that names the check ledger file or the data folder it is in (not a folder above it) is held unless it is one plain read command (`cat`, `Get-Content`), with or without a ledger file: only the server writes there.

**When it cannot finish.** If the hook fails, or reading a call takes longer than its budget (2 s of reading from its start, and a 5 s wall clock for a payload over 8 KB), it holds every Bash and PowerShell call (the denial says the hook could not finish reading the command, and to run it in smaller parts), every edit of a manifest or of the ledger, and a payload under 8 MB that does not parse; any other call goes ahead. What it cannot read inside its bounds is held as not read, and the denial names the part: a requirement or manifest line over 64 KB, a version over 80 characters, a range or constraint over 1,000, an `npm pkg set` key over 600, TOML nested more than 100 levels, a manifest on disk or after the edit over 8 MB, a MultiEdit whose edit count times the file's size passes a fixed bound, a command over 2 MB that names an install, a ledger file over 4 MB or with more than 5,000 entries for one package, a TOML escape or multi-line string in a dependency, and a change to a `pnpm-workspace.yaml` in which any line is not plain, that is, not a `key:` header, a `- 'entry'` item or a `key: value` with a plain or simply quoted value (the denial says to rewrite it as plain `name: version` lines). A payload over 8 MB that does not parse, or one over 64 MB, is not read whole and is held like a failure of the hook: every Bash and PowerShell call, every manifest edit, and any payload whose tool cannot be found in its first 64 KB. A call whose stdin is still open after 8 s is judged when its whole payload has arrived, and treated as a failure of the hook when it has not. Claude Code stops a hook after 10 s and then lets the call through.

**What it does not see.** Each of these goes ahead unchecked:

- commands that let the package manager choose versions without naming a package: `npm audit fix` (also with `--force`), `pnpm audit --fix`, `npm update`, `pnpm up`, `yarn upgrade` or `bun update` with no name or inside the manifest's range, `cargo update`, `cargo upgrade`, `poetry update`, `uv tool upgrade`, `go mod tidy`, `go get -u ./...`. Run `vulnerability_scan` after them;
- runners that fetch a package and run it: `npx pkg@v`, `pnpx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx`, `uvx`, `uv tool run`, `uv run --with pkg`, `pipx run`, `npm init` and the `create` commands, `go run mod@v`, `cargo binstall`. A runner that runs a package manager (`npx pnpm add x@1`) is read as that command;
- settings that change what a name resolves to when they live in files (`.npmrc`, `pip.conf`, `uv.toml` or pyproject's `[tool.uv]`, a lockfile edited by hand and installed with `npm ci`), when a config command writes them before the install in the same call (`npm config set`, `pip config set`, `poetry source add`, `go env -w`, `git config url.<x>.insteadOf`), or when a variable such as `HOME`, `APPDATA`, `CARGO_HOME` or `GOENV` points the manager at other config files;
- a manifest, requirements file or lockfile changed by a shell command (a redirection, `sed -i`, `tee`, a script) rather than the Edit, MultiEdit or Write tool;
- a program or script that runs an install (a make target, `npm run x`, `pwsh -File`, code given to `node -e` or `python -c`), and a package manager name the shell assembles or decodes;
- installs through pipenv, pdm, rye, pixi, hatch, conda, `pipx inject`, gem, composer and dotnet, and commands run inside a container;
- a pip requirement with more than eight version clauses in a `pyproject.toml` array;
- the release a package manager picks for a name given without a version when it is not the registry's newest: where the hook has placed the install it judges the newest, and the manager may still install another: a release the lockfile or an installed tree holds when no project file names the package (npm, pnpm, Yarn 1 and Bun were measured not to; uv, Poetry, Cargo and go were not measured), the newest that fits this Node, Python or Rust (`engines`, `requires-python`, `rust-version`), the release `latest` names when it is not the highest, or the copy pip finds installed (`pip install x` keeps it);
- a change of folder the hook cannot see: a shell function or alias named `cd`, a profile or a script sourced in an earlier call, a PowerShell script or function that calls Set-Location; and settings and pins in files it does not read (`.npmrc`, `.yarnrc.yml`, `bunfig.toml`, `.pnpmfile.cjs`, `pip.conf`, `uv.toml`, `Pipfile`, `deno.json`, `requirements.in`, `constraints.txt`);
- overrides, resolutions, catalogs, `[patch]` and workspace pins in the project, which can make the manager install another release than the one the command names: the hook judges those entries when they are edited, not when a command meets them. After a Bash or PowerShell command in which a package manager ran an install, add, update, sync or ci, package named or not (`npm ci`, `pnpm install --frozen-lockfile`, `yarn`, `pip install -r`, `uv sync`, `poetry install`, `cargo fetch`, `cargo build`, `go mod download`), the hook adds one line of advice, never a denial: "The package manager decides the releases actually installed. Run vulnerability_scan to check them.";
- a command that removes a folder above the data folder (the ledger guard names the ledger file and its own folder only);
- the allow lists of options are lists, not proofs: each option on them was tested not to change the named release in the tool versions tested, and another version of a tool may differ.

**Modes.** `FOURDA_GUARD=advise` never denies (the ledger guard included) and, after a manifest edit, tells the agent which versions moved and which calls check them; `FOURDA_GUARD=off` turns the hook off. `FOURDA_GUARD` is the user's setting, and every denial tells the agent not to change it. The hook and the server must share a data folder: with `FOURDA_MCP_HOME` set for the server, Claude Code's environment needs the same value. Beside a server older than 6.5.0, which records no verdict and starts no ledger, the hook denies nothing but a call that names the ledger, and advises after a manifest edit as it did before 6.5.0; a server from 6.5.0 on starts the ledger, empty, when it starts serving, and finishes writing it before it exits. Removing the ledger file turns the other denials off until the server starts again.

## Standalone vs. Full Mode

The MCP server works without the desktop app. It keeps a small local database in your user data folder (`%LOCALAPPDATA%\4da-mcp`, `~/Library/Application Support/4da-mcp` or `~/.local/share/4da-mcp`, never inside your repository) and scans your project on every start:

| Capability | Standalone | With 4DA Desktop |
|------------|-----------|-------------------|
| Upgrade impact (changelog, breaking changes, your call sites) | Yes | Yes |
| Vulnerability scanning (OSV.dev) | Yes | Yes |
| Dependency health (4 registries) | Yes | Yes |
| Upgrade planner | Yes | Yes |
| Pre-install dependency check | Yes | Yes |
| Ecosystem news (Hacker News, on request) | Yes | Yes |
| Pre-task intelligence briefing | Yes | Yes |
| Tech stack detection + resolved versions | Yes | Yes |
| Decision memory + alignment checking | Yes | Yes |
| Agent memory (cross-session) | Yes | Yes |
| Developer news judged against your stack (the app's feed) | -- | Yes |
| Actionable signals + knowledge gaps | -- | Yes |
| The analysis layer (Signal Chains, Knowledge Gaps, temporal analysis) | -- | Yes |

**With the desktop app attached** the dependency tools still read every lockfile under the project root from disk, with the same `coverage`: the same project gives the same packages, counts and coverage either way, and a sub-project the app has not indexed is not lost. The app's database supplies the app-backed tools (marked * above), decisions and memory, and the app's stored plan for `upgrade_planner` with `project_path: "*"`; a scan never writes to it.

**Supported app versions.** This server is tested against 4DA v1.0.3 (schema 124, plan format 4) through the app's main branch of 2026-11-22 (schema 131, plan format 5). With an app outside that range attached the server keeps serving (an answer it cannot serve from that database says which side to update, it does not just fail), and `get_context` and every answer that reads or writes the app's data carry `_meta.app_compatibility` (`status`: `app_older_than_supported` or `app_newer_than_tested`, the app's schema and plan format, the supported range, and a `note` saying whether to update the app or this server).

## Transports

**stdio** (default) -- works with all MCP hosts:
```bash
npx @4da/mcp-server@6.5.1
```

**Streamable HTTP** -- for remote or multi-client setups:
```bash
npx @4da/mcp-server@6.5.1 --http --port 4840
```

The HTTP transport binds to `127.0.0.1` by default and applies a `Host`-header
DNS rebinding guard to every request. Exposing it beyond this machine requires
a shared secret:

```bash
MCP_AUTH_SECRET=<same value as the relay's JWT_SECRET> \
MCP_ALLOWED_HOSTS=mcp.internal \
  npx @4da/mcp-server@6.5.1 --http --host 0.0.0.0
```

Only `localhost`, `::1` and an IPv4 address in 127.0.0.0/8 are loopback; any
other `--host`, a name such as `127.example.com` included, is a non-loopback
bind. Without `MCP_AUTH_SECRET` a non-loopback bind is refused at startup. With
it, every request must carry a Bearer token whose HMAC-SHA256 signature
verifies against that secret, and the token's role is enforced per tool
(`viewer` is read-only; `member` and `admin` may write). Each part of the token
must be base64url with no padding, and the signature in its one canonical spelling;
anything else is refused with 401. Put TLS in front of it.

JSON-RPC batches are refused with `-32600`, as on stdio: MCP removed them in
protocol revision 2025-06-18. A request that speaks 2025-03-26 or earlier (its
`MCP-Protocol-Version` header, an `initialize` in the batch, or no version at
all, which the transport spec reads as 2025-03-26) is still served, because
that revision requires a server to accept batches.

HTTP mode serves through `@hono/node-server`, and refuses to start when the copy
it would load is older than 2.1.6 (every 1.x release and every 2.x release
below 2.1.6 has a known advisory). That happens when the folder the server was
installed into already held an older copy, which npm keeps; the message names
the version. Install `@hono/node-server@^2.1.6` in that folder, or start the
server with npx. A version it cannot read is not refused. The stdio server does
not load it.

**HTTP mode is single-tenant.** A token's `team_id` is verified but not used to
separate data: every authenticated client shares one database, one agent memory
and one set of decisions, and `project_path` lets any authenticated client scan
any directory on the host the server can read. Run one server per team (or per
trust boundary), and only behind clients you would give that access.

## CLI Reference

```
npx @4da/mcp-server@6.5.1              # Start server (stdio)
npx @4da/mcp-server@6.5.1 --http       # Start server (Streamable HTTP)
npx @4da/mcp-server@6.5.1 --setup      # Auto-configure your editors
npx @4da/mcp-server@6.5.1 --doctor     # Check the install (exit code 1 when a check fails)
npx @4da/mcp-server@6.5.1 --version    # Print version
```

`--doctor` prints one line per check (in colour only on a terminal, and never with `NO_COLOR` set): the Node.js version, the SQLite driver, the data folder (a folder the server cannot write to fails), the server's own database, the cache (on disk or in memory, and why) and the app database, each with its path and state; build freshness in a repository checkout; the semantic recall provider; the proxy when one is set; whether OSV.dev and each registry answer; and a "Server version" warning when a session has seen a newer release. When it finds the server's own database empty (0 bytes) or without tables, it completes it in place, as a tool call would, and says so as a warning: anything that file was meant to hold is not in it. It exits 1 when any check fails, among them a server's own database it cannot open or complete, and a `FOURDA_DB_PATH` that names no file or a file with no tables. An app database the app has not finished setting up, or a database of this server's own format that `FOURDA_DB_PATH` names, is a warning that says why it is not used. The app database is only read.

## Limits

The server reads repositories it did not write, so everything it reads is bounded, and a bound that is hit is reported, never passed off as a clean result.

- **Time.** A tool call has 20 s (`FOURDA_CALL_BUDGET_MS`); the walk that finds a project's lockfiles has 10 s (`FOURDA_WALK_BUDGET_MS`), 20,000 directories, 4 levels and 256 projects. Past a walk bound the answer is a partial scan (`coverage.complete: false`), and `what_should_i_know`, `upgrade_planner` and `dependency_health` lead with NOT CHECKED naming the walk.
- **Size.** A lockfile or manifest over 64 MB is not read and is reported as UNREADABLE. A `.gitignore` over 1 MB, its rules past 5,000, and a pattern over 1,024 characters are not applied; a negation that cannot be applied re-includes everything below its file, so a limit can only make the scan cover more.
- **Arguments.** A version or constraint is at most 256 characters, a package name 512. `what_should_i_know` reads at most 100 `packages` entries and 100 `not_packages` words; a task is read for at most 100 packages, and a word longer than 300 characters is not read.
- **Place.** A drive or filesystem root and the operating system's own directories (`C:\Windows` and below, `/usr`, `/etc`, `/System` and the like) are not scanned: pass `project_path` with your project's root, or set `FOURDA_PROJECT_DIR`.

## Behind a proxy

Set `HTTPS_PROXY` (and `HTTP_PROXY`, `NO_PROXY`, in upper or lower case) in the server's environment (the `env` block of the MCP server entry) and every OSV.dev, registry and search lookup goes through that proxy, on every supported Node; nothing else to set. Hosts `NO_PROXY` names are reached directly. A proxy that cannot be reached, or refuses a request, makes the lookup fail, and the answer says NOT CHECKED: nothing is ever retried around the proxy. `dependency_check` then starts its summary with NOT CHECKED when no item could be checked, and `_meta.offline_note` says that `FOURDA_OFFLINE` is not set and the network, a proxy or OSV.dev failed. The server uses undici's `EnvHttpProxyAgent` for this (`undici`, MIT, pinned). An embedding provider you configure is the exception: it uses Node's own `fetch`, which honours the proxy on Node 24.14+, or on 22.21+ started with `NODE_USE_ENV_PROXY=1`.

The first lines of the server's stderr, and `npx @4da/mcp-server@6.5.1 --doctor`, say so whenever a proxy variable is set.

## FAQ

**Does this send my code anywhere?**
No. When a tool needs them (never at startup), the server sends public package names and versions to public APIs ([OSV.dev](https://osv.dev), npm registry, crates.io, PyPI, Go proxy), never a private package's name, downloads the target version's archive from the package's own registry for `upgrade_impact` (and reads GitHub release notes only if you set `FOURDA_GITHUB_CHANGELOG=true`), and, only when you call `ecosystem_pulse`, sends a few dependency names as search terms to [HN Algolia](https://hn.algolia.com/api). No source code, no file paths, no personal data: the call-site scan runs locally. Set `FOURDA_OFFLINE=true` to disable all network calls. (The sole exception is opt-in OpenAI embeddings — see the network note above.)

**How does this compare with GitHub's dependency tool for agents?**
GitHub's hosted MCP server has `check_dependency_vulnerabilities` (dependabot toolset). It needs a GitHub token and reports high and critical advisories and malware. In one comparison on 2026-11-11 (216 identical cases, ground truth from OSV.dev, this server at 6.2.7) it was faster (median 1.2 s against 2.5 s) and covers Maven and .NET, which this server does not read; it missed 102 of 178 known-bad versions, mostly medium and low advisories and RustSec / PyPA / Go-only records, which this server reports, and it does not judge nonexistent, yanked, deprecated or days-old releases. The cases and results of that comparison are not published in this repository, so it cannot be re-run from here: read it as one dated measurement of 6.2.7. This server needs no account and runs on your machine.

**Do I need the 4DA desktop app?**
No. These work standalone: upgrade impact, pre-install dependency checks, vulnerability scanning, dependency health, upgrade planning, ecosystem news, pre-task briefings, project context, decision memory, alignment checking, and agent memory. The desktop app is where the same engine runs day to day: one worklist across every project on the machine, a morning Brief of what changed in your stack, and an Upgrade Plan. With it installed, your agent also gets signals, knowledge gaps, developer news judged against your stack, Developer DNA and feedback.

**Which AI tools does this work with?**
Any tool that supports [MCP](https://modelcontextprotocol.io): Claude Code, Claude Desktop, Cursor, Windsurf, VS Code (Copilot), and any custom MCP client.
